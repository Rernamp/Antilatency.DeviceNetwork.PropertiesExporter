# Antilatency.DeviceNetwork.PropertiesExporter

Консольная утилита для периодического чтения свойств устройства Antilatency через Antilatency Device Network (ADN) и записи их значений в CSV. При включённом режиме замеров дополнительно считает время чтения каждого свойства и строит по нему статистику.

Типичные задачи:
- записать телеметрию устройства (напряжения, токи, температуры) за длительный период;
- понять, сколько времени прошивка тратит на чтение каждого свойства и какие свойства тормозят опрос.

## Как это работает

1. Утилита загружает библиотеку `AntilatencyDeviceNetwork` и создаёт сеть устройств (USB, при флаге `--ipDevices` также IP-устройства).
2. Ищет свободное (`Idle`) устройство, у которого значения всех свойств из `targetDeviceProperties` совпадают с заданными. Если за `--waitDeviceTimeout` устройство не найдено, утилита завершается с ошибкой.
3. Проверяет, что у устройства читаются все свойства из `dumpProperties`.
4. Открывает одну задачу чтения свойств (property task) на весь прогон и `--samplesCount` раз читает все свойства из `dumpProperties`, выдерживая период `--period` между началами итераций.
5. Строки пишутся в CSV отдельным потоком, чтобы запись на диск не влияла на опрос.

## Сборка

Требования:
- Windows (используется `localtime_s`, SDK поставляется под Windows);
- CMake 3.10+;
- компилятор с поддержкой C++20 и `<format>` (Visual Studio 2022).

Зависимости подключены как git-сабмодули в [Dependencies/](Dependencies/): Antilatency SDK 4.5.0, CLI11, nlohmann/json, csv2.

```powershell
git clone --recursive https://github.com/Rernamp/Antilatency.DeviceNetwork.PropertiesExporter.git
cd Antilatency.DeviceNetwork.PropertiesExporter

# если репозиторий уже склонирован без сабмодулей
git submodule update --init --recursive

cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

Результат появится в `build/Release/`: исполняемый файл, библиотеки Antilatency SDK и `config.json` по умолчанию копируются туда автоматически.

Готовые сборки публикует GitHub Actions ([.github/workflows/cmake-build.yml](.github/workflows/cmake-build.yml)): артефакт `windows-build` при каждом push в `main`, архив в GitHub Release при push тега вида `1.2.3`, `release-*` или `build-*`.

## Запуск

```powershell
Antilatency.DeviceNetwork.PropertiesExporter.exe --config config.json --samplesCount 100 --period 50
```

### Параметры командной строки

| Параметр | По умолчанию | Описание |
|---|---|---|
| `--config <путь>` | — (обязательный) | Путь к JSON-конфигу |
| `--period <мс>` | `1` | Период между началами итераций чтения. Если итерация длится дольше периода, следующая начинается сразу |
| `--samplesCount <N>` | `10` | Количество итераций (строк в CSV) |
| `--waitDeviceTimeout <мс>` | `2000` | Сколько ждать появления целевого устройства |
| `--ipDevices` | выкл. | Искать также IP-устройства |
| `--printProgress` | выкл. | Печатать прогресс после записи каждой строки |
| `--measureTiming` | выкл. | Замерять время чтения каждого свойства и строить статистику |

Полный список параметров: `--help`.

## Конфиг

```json
{
    "targetDeviceProperties": {
        "sys/HardwareName": "Alt"
    },
    "dumpProperties": [
        { "propertyName": "sys/MCU/Voltage", "alias": "" },
        { "propertyName": "sys/MCU/Temperature", "alias": "Temperature" }
    ]
}
```

- `targetDeviceProperties` — по каким свойствам выбирать устройство. Все пары «свойство — значение» должны совпасть.
- `dumpProperties` — какие свойства читать, в каком порядке. Поле `alias` обязательно: если оно пустое, в заголовке CSV используется имя свойства, иначе — alias.

Оба списка не должны быть пустыми.

Примеры конфигов:
- [config.json](config.json) — базовый пример для Alt;
- [config.LedModuleTester.json](config.LedModuleTester.json) — все измерительные свойства для прошивки `FullBandRGB.LedModule.Tester`;
- [config.LedModuleTester.snapshot.json](config.LedModuleTester.snapshot.json) — снимок измерений той же прошивки: запуск замера, ожидание готовности, чтение всего снимка одной CSV-строкой.

Свойства читаются в том порядке, в котором перечислены. Если чтение одного свойства влияет на последующие (например, переключает общую опору АЦП), порядок в конфиге влияет на результат замеров.

### Триггер замера (`trigger`, необязательно)

Для прошивок, где чтение свойства возвращает последний замер, а новый нужно запустить явно. Перед каждой итерацией утилита записывает свойства из `write`, затем опрашивает `waitUntil`, пока оно не станет равно заданному значению, и только потом читает `dumpProperties`. Всё идёт в одной задаче свойств.

```json
"trigger": {
    "write": [ { "propertyName": "set/Measure/Start", "value": "true" } ],
    "waitUntil": { "propertyName": "sys/Measure/Done", "value": "true" },
    "pollPeriod_ms": 0,
    "timeout_ms": 2000
}
```

| Поле | По умолчанию | Описание |
|---|---|---|
| `write` | — (обязательное) | Что записать перед итерацией, по порядку |
| `waitUntil` | — (обязательное) | Какое свойство опрашивать и какого значения ждать |
| `pollPeriod_ms` | `0` | Пауза между опросами; 0 — подряд |
| `timeout_ms` | `1000` | Предел ожидания на итерацию. Не дождались — прогон останавливается, уже записанные строки и статистика сохраняются |

`--period` отсчитывается от начала итерации и включает запись и ожидание. Отклонённая запись прерывает прогон так же, как ошибка чтения.

**Защита от записи в несуществующее свойство.** На прошивках Antilatency запись в незарегистрированный ключ `set/...` не отклоняется, а создаёт файл с этим именем во флеше устройства. Поэтому перед прогоном каждое свойство триггера читается, и если хоть одно пустое (ключа нет), утилита завершается, ничего не записав.

## Выходные файлы

Файлы создаются в текущей рабочей директории, имя — время запуска в формате `ДД_ММ_ГГГГ_ЧЧ_ММ_СС`. Разделитель — `;`.

### `<время>.csv` — значения свойств

| Столбец | Описание |
|---|---|
| `Timestamp` | Локальное время итерации, `ДД/ММ/ГГГГ ЧЧ:ММ:СС` |
| `ElapsedTime_ms` | Время от начала записи до начала итерации, мс |
| `<свойство или alias>` | Значение свойства в виде строки |
| `<свойство>_us` | Только с `--measureTiming`: время чтения свойства, мкс |
| `ReadAll_us` | Только с `--measureTiming`: суммарное время чтения всех свойств в итерации, мкс |
| `Trigger_us` | Только с `trigger` и `--measureTiming`: время записи свойств `write`, мкс |
| `Wait_us` | То же: от конца записи до получения нужного значения `waitUntil`, мкс |
| `WaitPolls` | То же: сколько раз прочитано `waitUntil` |
| `Cycle_us` | То же: `Trigger_us + Wait_us + ReadAll_us` — время получить свежий набор значений, мкс |

### `<время>_timing.csv` — статистика времени чтения

Создаётся только с `--measureTiming`, та же таблица выводится в консоль. По одной строке на каждое свойство и итоговая строка `ReadAll`, а с `trigger` — ещё строки `Trigger`, `Wait`, `WaitPolls`, `Cycle`:

`Count`, `Min_us`, `Mean_us`, `Median_us`, `P95_us`, `P99_us`, `Max_us`, `StdDev_us`, `Total_us`, `Share_%` (доля свойства в общем времени чтения; у строк триггера пустая — они не входят в `ReadAll`).

Время замеряется на стороне ПК вокруг каждого вызова `getStringProperty`, т.е. включает передачу запроса и ответа через ADN, а не только работу прошивки. Задача чтения свойств открывается один раз на весь прогон, поэтому её открытие и закрытие в замеры не входят. Первые итерации могут быть медленнее остальных из-за прогрева.

Пример замера:

```powershell
Antilatency.DeviceNetwork.PropertiesExporter.exe --config config.LedModuleTester.json --samplesCount 500 --period 0 --measureTiming
```

## Поведение при ошибках

- Устройство не найдено, не читается одно из свойств при проверке, не удалось открыть задачу чтения или создать CSV — утилита завершается с кодом `-1`.
- Ошибка чтения во время записи (например, устройство отключили) — прогон прерывается, но уже прочитанные строки и статистика по ним сохраняются.
